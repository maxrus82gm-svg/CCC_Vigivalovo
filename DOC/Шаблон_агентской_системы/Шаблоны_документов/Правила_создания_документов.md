# Правила создания документов

## Назначение

Документ описывает правила создания и обновления Markdown-документов в проекте `{{PROJECT_NAME}}`.

## Базовые правила

- Документы создаются только по задаче пользователя или активной задаче в `{{MAIN_TASK_FILE}}`.
- Документы сохраняются в Markdown.
- Кодировка: UTF-8.
- Русский текст должен читаться нормально.
- Использовать настоящие переносы строк.
- Не записывать файл одной строкой.
- Не вставлять текстовую пару backslash+n вместо переносов.
- Не экранировать Windows-пути двойными слэшами.
- Не менять `.obsidian` без разрешения.
- Не менять реальные конфиги агентов без прямой задачи.

## Правила папки шаблона агентской системы

`Шаблон_агентской_системы` — это рабочая площадка для сборки будущего единого документа-матрицы правил. Сейчас матрица строится здесь на реальном примере `{{PROJECT_NAME}}`, но не используется как рабочий набор правил текущего проекта `{{PROJECT_NAME}}`.

Папка универсального шаблона агентской системы находится здесь:

```text
{{DOC_FOLDER}}\Шаблон_агентской_системы
```

Если пользователь прямо поставил задачу создать, собрать, перенести, проверить, изменить или удалить будущий документ-матрицу правил, агент обязан сначала читать документы шаблона в порядке:

```text
README_как_переносить.md
MANIFEST_структуры.md
00_Паспорт_проекта.md
02_Карта_переменных.md
01_Правило_подгонки_под_новый_проект.md
03_Чеклист_проверки_переноса.md
04_Dry_run_пример_переноса.md
```

Изменения в шаблоне и изменения в рабочих правилах проекта не должны расходиться по смыслу. Если новое универсальное правило добавляется в шаблон и оно влияет на текущую работу проекта, агент добавляет отражение этого правила в рабочие документы `{{DOC_FOLDER}}`.

Если новое правило добавляется в рабочие документы и должно переноситься в будущие проекты, агент добавляет его отражение в шаблонные документы с placeholders вида `{{PROJECT_NAME}}`, `{{PROJECT_ROOT}}`, `{{DOC_FOLDER}}`.

В обычных задачах текущего проекта агент не берёт инструкции из `Шаблон_агентской_системы`, не подменяет ими рабочие правила и не передаёт их субагентам как источник правил.

Если в папку шаблона добавлен новый обязательный файл, агент обновляет `MANIFEST_структуры.md` и при необходимости `README_как_переносить.md`, чтобы следующий агент не пропустил этот файл.

## Obsidian links

Если проект использует Obsidian, новые документы связываются через Obsidian links, когда это нужно проекту:

```text
[[Название_документа]]
```

## Правило русских имён документов

Все рабочие документы агентской системы и проектной Obsidian-документации должны называться по-русски.

Это касается:

- правил;
- задач;
- отчётов;
- истории задач;
- карт чтения;
- паспортов проекта;
- Obsidian-документов;
- шаблонов документов;
- форм отчётов;
- пользовательских заметок проекта;
- рабочих Markdown-документов агентской системы.

Английские, оригинальные или технические имена допускаются, если файл относится к самому проекту как техническому продукту, серверу, игре, внешнему инструменту, коду, конфигам, модам, Workshop, логам, сохранениям, базе данных, служебной структуре или внешнему стандарту.

Не переименовывать без отдельной явной задачи пользователя:

- `.git`;
- `.obsidian`;
- `README.md`;
- файлы запуска;
- исполняемые файлы;
- конфиги;
- файлы кода;
- файлы модов;
- файлы логов;
- файлы сохранений;
- базы данных;
- служебные папки инструментов;
- файлы, имя которых ожидает внешняя программа.

При создании новых рабочих документов агентской системы агент обязан выбирать русское имя файла.

При работе с техническими файлами проекта агент обязан сохранять оригинальные имена, потому что переименование может сломать запуск, сборку, сервер, моды, конфиги, сохранения или внешний инструмент.

Если задача требует создать новый документ, агент сначала выбирает русское имя. Английское имя допускается только при прямой технической необходимости или явном разрешении пользователя.

## Правило единого большого и малого блока

Когда ChatGPT готовит задачу для агента, он обязан выдавать большой блок и малый блок как два отдельных цельных фрагмента.

Большой блок:

- предназначен для вставки в `БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА` файла `{{MAIN_TASK_FILE}}`;
- должен идти одним непрерывным куском;
- не должен быть разорван пояснениями, комментариями или вторыми кодовыми блоками;
- должен содержать весь scope задачи: цель, контекст, разрешённые файлы, запреты, проверки, формат отчёта и правило очистки `БЛОК 1`.

Малый блок:

- предназначен для отправки агенту в чат;
- должен идти отдельным цельным куском после большого блока;
- не должен смешиваться с большим блоком;
- не должен расширять scope и не должен отменять Git-политику без прямого разрешения пользователя.

Правильный формат ответа ChatGPT при подготовке задачи:

1. Один цельный большой блок для `БЛОК 1`.
2. Один цельный малый блок для чата агенту.

Запрещено выдавать большой блок частями, если пользователь просит готовую задачу для вставки.

## Проверка перед завершением

- Документ находится в разрешённом scope.
- Нет дубля уже существующего документа.
- Markdown читается нормально.
- UTF-8 сохранён.
- Нет текстовой пары backslash+n вместо переносов.
- Нет случайных путей чужого проекта.
